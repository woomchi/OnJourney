**문서명**: 실시간 버스/기차 도착 정보 연동 기술 명세서  
**버전**: 1.1  
**작성일**: 2026년 8월 13일  
**최종 수정**: 2026년 8월 13일 (TAGO 주축 구조 반영)  
**대상 프로젝트**: On-Journey (다중 경로 검색 기반 여행 계획 앱)  
**범위**: 실시간 버스 도착 정보 조회, 열차/시외버스 예약 정보, 지역별 데이터 통합

---

## 📋 개요

### 목표

On-Journey의 다중 경로 검색 결과에 **실시간 대중교통 정보**를 추가하여 사용자에게 다음을 제공:

- ✅ 정류장에서의 다음 버스 도착 시간 (5분 단위 정확도)
- ✅ 기차/버스 예약 가능 여부 및 요금
- ✅ 지역별 서로 다른 데이터 소스의 자동 통합
- ✅ 실시간 정보 신뢰도 시각화
- ✅ 네트워크 장애 시에도 캐시된 데이터로 서비스 지속

### 주요 기능 범위

| 기능 | 데이터 출처 | 갱신 주기 | 지역 범위 |
|------|----------|---------|---------|
| **버스 도착 정보** | 국토교통부 TAGO (주축) + 시도별 API (시내버스 보완) | 15~30초 | 전국 (서울 포함 14개 지역, 시내버스 보완: 경기·부산) |
| **열차 운행 정보** | ODsay / 국토교통부 TAGO | 실시간 | 전국 KTX, 새마을, 무궁화, 청춘호 |
| **고속/시외버스** | 공공데이터포탈 | 30분~1시간 | 전국 터미널 기준 |
| **지하철 시간표** | ODsay API | 정적 (일일 시간표) | 수도권, 부산, 대구, 광주, 대전 |

### 비즈니스 가치

- **사용자 경험**: 정류장 대기 시간 정확히 예측 가능
- **경쟁력**: 네이버 지도 다중 길찾기 한계 극복
- **신뢰도**: 공식 공공 데이터로 신뢰성 확보
- **확장성**: 지역별 API 추상화로 향후 더 많은 지역 추가 용이

### 1. TAGO 버스도착정보 (주축 — 전국)

> **역할**: 전국 대부분의 버스 도착 정보를 포괄하는 **Primary API**. 서울을 포함한 14개 시도를 단일 엔드포인트로 조회.  
> **호출 순서**: 항상 첫 번째로 호출. 지역별 보완 API가 있으면 이 결과와 머지.

#### 순차 호출 흐름

```
① TAGO API 호출 (전국 주축)
   → cityCode + nodeId로 요청
   → 전국 버스 도착 정보 수신
        │
        ▼
② 지역 확인 — 보완 API 존재 여부 판별
   - 경기 → ✅ 경기도 버스도착정보 추가 호출
   - 부산 → ✅ 부산 버스정보시스템 추가 호출
   - 그 외 → TAGO 결과만 사용
        │
        ▼
③ [경기·부산만] 보완 API 호출
   → 시내버스 상세 정보 수신
        │
        ▼
④ 머지
   - 동일 노선: 보완 API 우선 (신뢰도 0.85)
   - TAGO에만 있는 노선: TAGO 데이터 사용
```

#### 개요
- **공식명**: 국토교통부_TAGO_버스도착정보
- **제공기관**: 국토교통부
- **URL**: `https://apis.data.go.kr/1613000/BusSttnInfoInqireService/getArrivalInfoList`
- **프로토콜**: HTTPS GET
- **응답 포맷**: JSON
- **인증**: ServiceKey (공공데이터포탈에서 발급)
- **갱신 주기**: 15~30초 (지역별 차이)
- **신뢰도**: 0.75~0.85 (지역별 차이)

#### 요청 파라미터

| 파라미터 | 필수 | 타입 | 설명 | 예시 |
|---------|------|------|------|------|
| `ServiceKey` | Y | String | URL 인코딩된 API 키 | `xxxxxxxxxxx` |
| `arsId` | Y | String | 정류소 ID (하이픈 제거) | `19182` |

**파라미터 주의사항**:
- arsId는 ODsay API에서 `arsID` 필드로 반환됨
- 포맷: "19-182" → "19182" (하이픈 제거)
- ServiceKey는 반드시 URL 인코딩하여 전달

#### 응답 구조

```
XML 응답:

│  ├─ msgHeader

| 필드 | 의미 | 범위 | 예시 |
|------|------|------|------|

#### 버스 타입 분류

서울시 버스 번호 규칙:
- **간선버스** (파랑): 10~99 (숫자만)
- **광역버스** (빨강): 100~199 / 200~299
- **지선버스** (초록): 300~399 / 400~899  
- **순환버스** (노랑): X00 형식

**마지막 자리로 구분**:
- `-1`: 광역버스 (express)
- `-2`: 제한버스 (limited)
- `-3`: 순환버스 (circulation)
- 없음: 일반버스 (normal)

### 2. 경기도 버스 도착 정보

#### 개요
- **공식명**: 버스도착정보 조회 서비스
- **제공기관**: 경기도청
- **URL**: `https://apis.data.go.kr/6410000/busstationservice/getBusArrivalInfoItem`
- **프로토콜**: HTTPS GET
- **응답 포맷**: JSON
- **인증**: ServiceKey (공공데이터포탈에서 발급)
- **갱신 주기**: 20초
- **신뢰도**: 0.85 (높음)

#### 요청 파라미터

| 파라미터 | 필수 | 타입 | 설명 | 예시 |
|---------|------|------|------|------|
| `ServiceKey` | Y | String | URL 인코딩된 API 키 | `xxxxxxxxxxx` |
| `stationId` | Y | String | 정류장 ID | `123456` |
| `pageNo` | N | Integer | 페이지 번호 (기본값: 1) | `1` |
| `numOfRows` | N | Integer | 결과 갯수 (기본값: 10) | `10` |

**파라미터 주의사항**:
- stationId는 ODsay API에서 `localstationID` 필드로 반환됨
- ServiceKey는 반드시 URL 인코딩하여 전달

          "locationNumber1": "10",  // 정류소번호
          "stopName": "강남역"      // 도착지명
        },
        {
          ...
        }
      ]
    }
  }
}
```

#### 데이터 의미

| 필드 | 의미 | 범위 | 예시 |
|------|------|------|------|
| `routeName` | 버스 노선번호 | 1~4자리 | "200", "5012" |
| `predictedTime1` | 첫번째 버스 도착시간 (초) | 0~999 | "180" (3분) |
| `predictedTime2` | 두번째 버스 도착시간 (초) | 0~999 | "600" (10분) |
| `locationNumber1` | 정류소 번호 (거리 추정용) | 1~ | "10" |
| `stopName` | 버스 도착지명 | 지명 | "강남역", "판교" |

#### 버스 타입 분류

경기도 버스 번호 규칙:
- **광역/간선** (파랑): 100~299
- **지선** (초록): 300~899
- **마을버스** (빨강): 대부분 지원 안함

#### 에러 코드

| 코드 | 상황 | 대응 |
|------|------|------|
| 00 | 정상 | 데이터 반환 |
| 01 | 필수 입력값 누락 | 요청 파라미터 재확인 |
| 02 | 존재하지 않는 정류소 | fallback API 사용 |

### 2. 경기도 버스도착정보 (시내버스 보완)

> **역할**: 경기도 시내버스에 대한 **Supplement API**. TAGO 호출 후 경기 지역으로 확인되면 추가 호출하여 결과를 머지.

#### 개요
- **공식명**: 버스도착정보 조회 서비스
- **제공기관**: 경기도청
- **URL**: `https://apis.data.go.kr/6410000/busstationservice/getBusArrivalInfoItem`
- **프로토콜**: HTTPS GET
- **응답 포맷**: JSON
- **인증**: ServiceKey (공공데이터포탈에서 발급)
- **갱신 주기**: 20초
- **신뢰도**: 0.85 (높음)

#### TAGO와의 머지 정책

| 상황 | 처리 방식 |
|------|----------|
| 동일 노선번호 존재 | 경기 API 데이터 우선 (신뢰도 0.85) |

## 💾 캐싱 전략

### 3단계 캐싱 계층화

#### L1: 프론트엔드 메모리 캐시

- **저장소**: 브라우저 메모리 (React State / React Query / SWR)
- **TTL**: 1~5분
- **범위**: 현재 사용자만
- **우점**: 즉각적 응답, 네트워크 비용 0
- **단점**: 페이지 새로고침 시 초기화

**L1 캐시 사용 시기**:
- 사용자가 동일 정류장을 반복 조회 (5분 이내)
- 자동 갱신 중 화면 전환

#### L2: 백엔드 Redis 캐시

- **저장소**: Redis (서버 인스턴스)
- **TTL**: 지역별 상이 (10~30초)
- **범위**: 모든 사용자 간 공유
- **우점**: 중복 API 호출 방지, 빠른 응답
- **단점**: 캐시 미스 시 공공 API 호출

**지역별 TTL**:
| 지역 | TTL | 사유 |
|------|-----|------|
| 서울 | 10초 | API 갱신 빈도 높음 |
| 경기 | 20초 | 중간 갱신 주기 |
| TAGO | 30초 | 갱신 주기 낮음 |
| 부산 | 15초 | 중간 갱신 주기 |

#### L3: 공공 API (실시간 소스)

- **저장소**: 공공데이터포탈 / ODsay 서버
- **TTL**: 최신 정보 (캐시 없음)
- **갱신 주기**: 10~30초 (API별 상이)
- **신뢰도**: 1.0 (공식 데이터)

**L3 호출 조건**:
- L2 캐시 미스
- 사용자가 "새로고침" 버튼 클릭
- 캐시 TTL 만료

## 🔄 에러 처리 및 복구 전략

### 에러 분류

#### 1. 재시도 가능 (Retryable) 에러

| 에러 | HTTP 상태 | 대응 | 재시도 간격 |
|-----|---------|------|----------|
| 타임아웃 | 504 | 3회 재시도 | Exponential backoff (1s, 2s, 4s) |
| 일시적 연결 오류 | ECONNREFUSED | 3회 재시도 | Exponential backoff |
| Rate Limit | 429 | 3회 재시도 | Retry-After 헤더 참고 |
| 서버 에러 | 5xx | 2회 재시도 | Exponential backoff |

#### 2. 재시도 불가능 (Non-retryable) 에러

| 에러 | HTTP 상태 | 대응 | 설명 |
|-----|---------|------|------|
| 인증 실패 | 401 / 403 | 폴백 캐시 | API 키 확인 필요 |
| 잘못된 요청 | 400 | 폴백 캐시 | 파라미터 형식 오류 |
| 리소스 없음 | 404 | 폴백 캐시 | 해당 정류소 없음 |
| 파싱 에러 | N/A | 폴백 캐시 | API 응답 형식 변경 |

### CORS 정책

**공공 API의 CORS 제한**:
- 대부분의 공공 API는 CORS 정책으로 인해 **프론트엔드에서 직접 호출 불가**
- **반드시 백엔드 API를 경유**해야 함

**백엔드 CORS 설정**:
- 프론트엔드 도메인 화이트리스트 설정
- 프로덕션: `https://on-journey.com` 등 명시
- 개발: `http://localhost:3000` 허용

### Rate Limiting 대응

**공공 API 제한**:
- 서울시: 시간당 1,000회 (프리 티어)
- 경기도: 시간당 1,000회
- TAGO: 시간당 1,000회
- ODsay: 정책별 상이

**대응 방안**:
1. **캐싱**: L2 Redis로 중복 요청 방지
2. **재시도**: Rate Limit 시 Retry-After 대기
3. **요청 큐잉**: 동시 요청 수 제한
4. **유료 업그레이드**: 필요 시 공공데이터포탈에서 업그레이드

## 📞 예상 질문 및 FAQ

### Q1. 왜 백엔드에서만 API를 호출하나요?

**A**: 공공데이터포탈의 모든 API는 CORS(Cross-Origin Resource Sharing) 정책을 적용하고 있어 **브라우저에서 직접 호출할 수 없습니다**. 따라서 백엔드를 경유하여 호출해야 합니다.

### Q2. 캐시 TTL이 왜 지역별로 다른가요?

**A**: 각 지역의 API 갱신 주기가 다르기 때문입니다. 서울시는 10초, 경기도는 20초 주기로 업데이트되므로, 캐시도 이에 맞춰 설정하여 데이터 신선도를 유지합니다.

### Q3. Rate Limit에 걸리면 어떻게 되나요?

**A**: 백엔드는 429 에러를 받으면 Retry-After 헤더를 참고하여 대기 후 자동으로 재시도합니다. 그래도 실패하면 **오래된 캐시 데이터를 반환**하고 신뢰도를 낮춥니다.

### Q4. 오프라인 상태에서도 작동하나요?

**A**: 캐시가 있다면 가능합니다. L1(프론트) 또는 L2(Redis) 캐시가 존재하면 그 데이터를 표시합니다(신뢰도 낮음).

### Q5. 어떤 지역을 먼저 지원해야 하나요?

**A**: 다음 순서를 권장합니다:
1. **경기** (경기도 주요 도시)
2. **부산** (2번째 도시)
3. **TAGO** (기타 지역)

### Q6. ODsay API 키는 꼭 필요한가요?

**A**: Fallback 용도로 권장됩니다. 주요 지역(서울/경기)에서 실패할 때 열차 정보 등을 제공할 수 있습니다.

### Q7. 신뢰도 점수는 어떻게 사용되나요?

**A**: UI에서 색상으로 표시하여 사용자에게 정보의 신뢰성을 알립니다.
- 🟢 0.85~1.0: 실시간 정보
- 🟡 0.60~0.84: 약간 오래된 정보
- 🔴 0.00~0.59: 캐시된 정보 (매우 오래됨)

### Q8. 비용이 들나요?

**A**: 공공데이터포탈 API는 **무료**입니다. 다만 다음 비용이 발생합니다:
- Redis 서버 (클라우드 호스팅)
- 백엔드 서버 (EC2, App Engine 등)
- 네트워크 비용 (극소)
