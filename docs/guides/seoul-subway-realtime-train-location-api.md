### 1. API 엔드포인트 및 요청방식

#### 기본 URL
```
http://swopenapi.seoul.go.kr/api/subway/[KEY]/json/realtimeStationArrival/[START_INDEX]/[END_INDEX]/[statnNm]
```

#### 요청 방식
- **HTTP Method**: GET
- **데이터 형식**: JSON / XML
- **응답 타입**: TYPE 파라미터로 지정

## ⏱️ 실시간 도착정보 정확도 향상을 위한 시간차 보정

### 시간차 발생 원인
- 데이터 수집, 가공, 전송 과정에서 지연 발생
- TOPIS 시스템에서 데이터 생성 시각(recptnDt)과 실제 열차 위치에 시간차 존재
- API 응답까지의 네트워크 지연

### 보정 방법 (중요)

#### barvlDt 기반 도착 예상시간 계산

**barvlDt** (열차도착예정시간)는 단위가 **초(second)**이므로, recptnDt 기준으로 예상 도착 시간을 계산합니다.

```
예상도착시간 = recptnDt + barvlDt(초)

예시:
- recptnDt: 2023-06-11 14:05:56
- barvlDt: 120 (초)
→ 예상도착시간: 2023-06-11 14:07:56
```

#### 시간차 보정 계산식

```
현재시간을 기준으로 정확한 도착 예상시간:
조정된도착시간 = recptnDt + barvlDt - (현재시간 - recptnDt)
             = barvlDt - (현재시간 - recptnDt)
             
또는 간단히:
남은시간(초) = barvlDt - (현재시간 - recptnDt의 경과시간)
```

#### 실제 예시

```
[시나리오 1: 정상 케이스]
- 현재시간: 2023-06-11 14:06:00
- recptnDt: 2023-06-11 14:05:56 (4초 전 데이터)
- barvlDt: 120 (초)

[계산]
경과시간 = 4초
남은시간 = 120 - 4 = 116초
예상도착 = 14:06:00 + 116초 = 14:07:56

→ 약 2분 후 도착
```

```
[시나리오 2: 시간차 보정 필요]
- 현재시간: 2023-06-11 14:07:00
- recptnDt: 2023-06-11 14:05:56 (64초 전 데이터)
- barvlDt: 120 (초)

[계산]
경과시간 = 64초
남은시간 = 120 - 64 = 56초
예상도착 = 14:07:00 + 56초 = 14:07:56

→ 약 1분 후 도착 (초기 예상보다 빨라짐)
```

#### 정확도 향상 전략

1. **recptnDt 신선도 검증**
   - recptnDt가 현재시간 대비 30초 이상 차이 → 시간차 보정 필수
   - recptnDt가 미래 시간(이상치) → 해당 데이터 필터링

2. **arvlCd (도착코드) 활용**
   - 0: 진입 → 매우 가까운 상태
   - 1: 도착 → 역 정차 단계
   - 2: 출발 → 역을 떠난 상태
   - 99: 운행중 → barvlDt 기반 추정 필요

3. **arvlMsg2, arvlMsg3 텍스트 활용**
   - UI 표시용으로 직접 사용 가능
   - 사용자 친화적 메시지 제공

4. **btrainSttus (열차종류) 고려**
   - 급행: 더 빠른 도착 시간
   - 일반: 기본 도착 시간
   - 특급/ITX: 최소 정차역만 포함

5. **다중 데이터 교차 검증**
   - 같은 역의 여러 열차 barvlDt 비교
   - 비정상적으로 큰/작은 값 필터링
   - 순번(ordkey) 기반 열차 순서 검증

### 관련 필드 활용 가이드

| 필드명 | 용도 | 활용 팁 |
|--------|------|--------|
| **recptnDt** | 데이터 신선도 판단 기준 | 현재시간과의 차이로 시간차 검증 |
| **barvlDt** | 도착 예상시간 계산 | 초 단위이므로 보정 시 필수 |
| **arvlCd** | 열차 상태 파악 | 0,1,2: 정확, 99: 추정 필요 |
| **arvlMsg2/3** | UI 메시지 표시 | 직관적 사용자 경험 제공 |
| **ordkey** | 열차 순번 및 거리 추정 | 1번째/2번째 열차 구분 및 거리 예상 |

| **btrainSttus** | 열차 종류 표시 | 급행/일반 구분으로 정확도 향상 |

## 📋 데이터 해석 가이드

### arvlCd (도착코드) 정의
- **0**: 진입 (역 진입 중 - 매우 곧 도착)
- **1**: 도착 (역에 정차 - 현재 역 도착)
- **2**: 출발 (역 출발 - 이미 떠남)
- **3**: 전역출발 (지난 역 출발)
- **4**: 전역진입 (지난 역 진입)
- **5**: 전역도착 (지난 역 도착)
- **99**: 운행중 (먼 거리, barvlDt 기반 추정)

### btrainSttus (열차종류) 정의
- **일반**: 모든 역 정차 (완행)
- **급행**: 주요 역만 정차
- **ITX**: 광역급행열차
- **특급**: 최소 정차역만 포함

### updnLine (상하행선) 정의
- **상행**: 시작 터미널 방향 (내선)
- **하행**: 종착 터미널 방향 (외선)

### lstcarAt (막차여부) 코드
- **0**: 일반 열차
- **1**: 막차 (마지막 열차)

### ordkey (도착예정열차순번) 구조 분석
```
ordkey = [상하행코드(1자리)][순번(1자리)][거리(3자리)][목적지(3자리)][급행여부(1자리)]

예: "0010060100"
- 상하행: 0 (상행/내선)
- 순번: 0 (첫번째 열차)
- 거리: 100 (6개 역 떨어짐)
- 목적지: 010
- 급행: 0 (완행)
```

## 🔍 API 호출 제한 및 정책

### 갱신 주기
- **실시간 갱신**: 분 단위 업데이트
- **과거 데이터**: 미제공 (실시간만 제공)
- **캐싱 권장**: 5~10초 단위 캐싱으로 불필요한 호출 감소

### 데이터 특성
- **방식**: API to API 전달 방식
- **데이터량**: 대용량 (분 단위 갱신)
- **신뢰성**: 현재 2호선 호출 정상화

### 활용 시 주의사항
1. **인증키 필요**: 각 포털에서 별도 신청 후 KEY 파라미터에 포함
2. **호출 한도**: 포털별 정책 확인 필수 (일반적으로 시간당 1,000회 이상)
3. **시간차 보정**: 필수 구현 (recptnDt + barvlDt 기반)
4. **역명 인코딩**: URL 인코딩 필수 (한글 역명)
5. **에러 처리**: RESULT.CODE 값 확인으로 오류 감지
