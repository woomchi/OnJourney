## 1. 프로젝트 요약

**OnJourney**는 n개의 경유지를 추가하고 드래그 앤 드롭으로 순서를 조정하면, 구간별 최적 경로와 이동수단(대중교통 / 차량 / 도보)을 자동 생성해주는 지도 기반 웹앱이다.

슬로건: *"당신의 모든 이동이 온전히, 여정이 되도록."*

한국어 '온전히'와 영어 'On-Journey'의 언어유희로, 문 밖을 나서는 순간부터 목적지에 닿기까지의 모든 평범한 이동을 하나의 소중한 여정으로 대한다는 철학을 담았다.

- **Circuit Breaker** (CLOSED → OPEN → HALF_OPEN 3상태): ODsay 연속 장애 보호
- **Rate Limiter**: ODsay 무료 플랜 1,000회/일 쿼터 보호
- **시간대별 캐시 전략**: 평일/주말 × 낮(4h TTL)/밤(30m TTL)

## 4. 기술적 도전과 배운 것

### 4-1. 네이버 지도 SDK — 무한 루프 함정

`react-naver-maps`는 컴포넌트 방식으로 추상화되어 있지만, 내부적으로 Native SDK와 상태를 공유하는 구조다. `useEffect` 내에서 지도 상태를 직접 건드리면 `idle` 이벤트가 재발화되어 무한 렌더링 루프에 빠지는 버그를 초기에 반복 경험했다. 이후 `useRef` + 이벤트 리스너 패턴으로 완전히 정착하여 해결했다. (`naver_map_guide.md` 문서화)

### 4-2. 경로 탐색 API 설계의 변천 — 그리고 근본적 한계의 발견

경로 탐색 아키텍처는 프로젝트 내내 진화했고, 그 끝에서 서비스 본질을 무너뜨리는 구조적 한계를 발견했다.

**1단계: 수단별 개별 호출 방식 (초기)**

초기 설계는 단순했다. 대중교통(버스/지하철)은 ODsay로, 도보는 직선 거리 기반 임시 Fallback으로 처리했다. 시외버스/기차는 구조적으로 더 복잡했다 — ODsay는 터미널↔터미널 구간 정보만 제공하기 때문에, 실제 문 앞부터 목적지까지의 이동은 별도로 처리해야 했다. 즉, 하나의 여정 구간에 대해 ① 터미널까지의 이동 ② 기차/시외버스 구간 ③ 도착 터미널에서 목적지까지, 총 3번의 API 호출을 연쇄적으로 발생시켜야 했다. 이 방식은 ODsay 무료 플랜(1,000회/일) 안에서 구간 수가 늘수록 병목을 일으켰고, 실제로 API 호출 한도를 초과하는 오류가 발생했다.

**2단계: TMAP 도보 + 지형 분류 도입**

도보 구간의 정밀도를 높이기 위해 TMAP 보행자 경로 API를 연동했다. 거기서 더 나아가 산악·해안 지형 GeoJSON 데이터베이스와 Turf.js BBox+PIP 2단계 지형 분류를 구현했다 — 일반 보행, 등산로, 해안 트레킹 등 경우의 수마다 다른 도보 경로를 제공하기 위해서였다. 이 작업 자체는 흥미로웠지만, 복잡도에 비해 실제 사용자에게 체감되는 차이가 크지 않다는 것을 점차 인식하게 됐다.

**3단계: ODsay 멀티모달 API로 통합**

ODsay API 명세를 다시 꼼꼼하게 읽다가 `maasRP` (멀티모달 경로탐색 API)를 발견했다. 이 API는 대중교통·도보·자전거·킥보드 등 모든 이동 수단을 하나의 요청으로 통합 처리해준다. 기존에 3번씩 연쇄 호출하던 시외버스/기차 구간 문제가 멀티모달 API 한 번으로 해결됐다. API 호출 횟수 병목도 사라지고, 응답 구조도 일관되어 코드가 크게 단순해졌다. 이 전환은 Phase 8의 핵심 개선이었다.

**그리고 근본적 한계를 발견했다**

멀티모달 API로 통합한 뒤, 실시간 도착 정보와 연동하는 과정에서 ODsay의 구조적 한계가 드러났다.

ODsay의 경로탐색 API는 **미리 계산된 고정 데이터베이스** 기반으로 작동한다. 출발 시간을 파라미터로 넘겨도, API는 그 시간에 맞는 실제 운행 시간표를 실시간으로 계산해 돌려주는 것이 아니라, 사전에 정형화된 경로 패턴 중 하나를 선택해 반환한다. 즉, **"지금 출발하면 몇 분에 어떤 버스/지하철을 타야 하는가"**라는 질문에 정확히 답하지 못한다.

예를 들어 오전 9시에 탐색한 경로와 오후 11시에 탐색한 경로가 실질적으로 동일한 노선을 반환하는 경우가 있었다. 심야에 운행하지 않는 버스가 포함된 경로가 그대로 제안되거나, 출발 시간 기준으로 가장 빠른 첫 번째 열차를 찾아주는 것이 아닌 패턴 기반의 "이 구간은 보통 이렇게 간다"는 정보를 제공하는 수준이었다.

이는 OnJourney의 핵심 가치인 **"여정 계획 → 실제 실행"** 사이의 다리를 놓는다는 목표를 달성하기 어렵게 만들었다. 경로 정보가 고정적이면, 실시간 도착 정보(버스/지하철 도착 칩)와 연동해도 사용자는 "지금 출발하면 정말 이 버스를 탈 수 있는가"를 신뢰하기 어렵다. 아무리 실시간 ETA를 정밀하게 파싱하고 시각 오프셋을 보정해도, 경로 자체의 출발 시간 반영 정확도가 낮으면 서비스의 본질이 흔들린다.

이 지점에서 더 이상의 고도화가 표면적인 정밀도 개선에 그칠 것이라는 판단이 섰다.

### 4-3. 지하철 ETA 정밀화 — 끝없는 보정의 세계

`arvlMsg2` 필드 하나를 파싱하는 데 전용 클래스(`SubwayMessageParser`)를 만들게 될 줄 몰랐다. 역명에 이중 공백, 중간 공백, 자모 분리(`ㅡ`, `ㅠ`) 오류가 실제 운영 데이터에서 빈번하게 발생했고, 이를 NFD→NFC 정규화 + Fuzzy Match로 처리했다. 또한 클라이언트 시각과 서버 시각이 최대 ±5초 차이가 나는 문제로 ETA 계산 오차가 누적되었고, `TimeOffsetManager`로 RTT 보정을 도입했다.

데이터 품질 문제는 코드로 해결할 수 있는 한계가 있었다. 공공기관 API의 응답 품질은 제공자가 바꾸지 않는 이상 개선할 수 없다.

### 4-4. Zustand v5 슬라이스 패턴

초기 단일 스토어 구조에서 Phase 7~8 시점에 `journeyDataSlice` / `mapSlice` / `uiSlice`로 분리했다. 기능 추가보다 리팩토링에 더 많은 시간이 들었지만, 이후 유지보수와 디버깅이 눈에 띄게 쉬워졌다. 처음부터 슬라이스 패턴을 적용했어야 했다.

### 4-5. @dnd-kit 전환

HTML5 Native DnD는 모바일 터치에서 동작하지 않는다. Phase 8에서 `@dnd-kit`으로 전환하면서 드래그 앤 드롭 UX가 안정화됐다. 이 결정은 늦었지만 반드시 필요했다.

### 4-6. 모바일 UX — 바텀 시트의 복잡성

`framer-motion` 기반 `CustomBottomSheet`는 스냅 포인트(0~4단계)와 내부 스크롤, 지도 줌 조정이 연동되는 복잡한 시스템이다. 바텀 시트 높이 변화에 따른 지도 카메라 패딩 재계산, 스크롤 방향 감지(바텀 시트 드래그 vs. 내부 콘텐츠 스크롤), 키보드 팝업 시 레이아웃 충돌 등 예상보다 훨씬 많은 엣지 케이스가 있었다.

## 5. 프로젝트를 마무리하는 이유

### 5-1. 경로 탐색의 근본적 한계 — 서비스 본질의 상실

OnJourney의 핵심 가치는 단순한 경로 안내가 아니라 **"지금 출발하면 실제로 어떻게 이동해야 하는가"**를 알려주는 것이었다. 여정을 저장해두고, 당일 실시간으로 확인하며, 계획대로 실행할 수 있어야 했다.

그런데 4-2절에서 서술했듯, ODsay의 경로탐색 API는 미리 계산된 고정 데이터베이스를 반환하는 구조다. 출발 시간이 달라져도 동일한 경로 패턴이 반환되는 경우가 있었고, 심야에 운행하지 않는 노선이 포함된 채로 경로가 제안되기도 했다. 이 문제를 인지한 뒤 `departureTime` 파라미터와 시간대별 캐시 키(평일/주말 × 낮/밤 4구간)를 도입하는 등 완화 전략을 시도했지만, 근본적으로 API가 실시간 시간표 기반으로 계산하지 않는다는 구조는 바꿀 수 없었다.

실시간 도착 칩(버스/지하철 ETA)을 아무리 정밀하게 만들어도, 그 기반이 되는 경로 자체가 "지금 이 시간에 맞는 경로"가 아닌 "일반적으로 이 구간은 이렇게 간다"는 패턴 정보라면, 서비스가 제공하는 신뢰도는 근본부터 흔들린다. 사용자는 화면의 ETA를 믿고 이동했다가 실제와 다른 상황을 맞닥뜨릴 수 있다.

이 지점이 명확해졌을 때, 더 이상의 고도화가 **표면적인 정밀도 개선**에 그칠 것이라는 판단이 섰다. 개선 방향이 없는 것은 아니다 — 카카오 모빌리티나 NAVER Maps 프리미엄 같은 상용 API는 실시간 시간표 기반 계산을 지원한다. 하지만 이를 도입하는 것은 개인 프로젝트의 비용 구조를 완전히 바꾸는 일이다.

### 5-2. 그 밖의 부차적 요인들

위의 핵심 이유에 더해 아래 요인들도 복합적으로 작용했다.

- **공공 버스 API의 지역 파편화**: 서울/경기/인천/부산/대전 각각 스펙이 달라 통합 유지보수 부담이 기하급수적으로 증가한다. 전국 커버리지를 달성하려면 광주, 울산, 세종 등 추가 연동이 필요하다
- **ODsay 정책 제약**: 영구 DB 구축 금지, 캐싱 최단시간 원칙이 있어 캐싱 전략 자체를 정책 경계선 위에서 운영해야 했다
- **공공 API 데이터 품질**: XML 기반 응답, 불안정한 서버, 역명 파싱 오류 등 데이터 품질 문제는 코드로만 해결할 수 있는 한계가 있다

### 5-3. 아이디어 자체는 유효하다

아이디어가 틀린 것이 아니라, 개인 개발자가 공개 API만으로 이 수준의 서비스를 구현하기에 생태계가 충분히 열려 있지 않다는 것을 확인했다. 카카오맵, 네이버 지도 등 대형 플랫폼이 이미 비슷한 방향으로 발전하고 있지만, 그들은 자체 운행 데이터와 실시간 시간표 데이터에 직접 접근할 수 있기 때문에 가능한 일이다.

- **점진적 리팩토링**: 기능 추가와 리팩토링을 병행하며 코드 품질을 유지했다. 특히 슬라이스 패턴, features/ 디렉터리 분리는 후반부 유지보수에 실질적인 도움이 됐다
- **Fallback 체계**: ODsay 장애, TMAP 실패, 공공 API 오류 등 모든 외부 API에 Fallback을 준비해두었다. Circuit Breaker + Rate Limiter 조합은 잘 작동했다
- **실제 API 연동**: 처음부터 Mock 데이터 없이 실 API를 연동하면서 진짜 문제를 빠르게 발견했다
- **모바일 우선 설계**: PWA + 바텀 시트 + GPS 트래킹까지 모바일 환경을 처음부터 고려한 설계가 나중에 큰 수정 없이 이어졌다

### 아쉬운 것

- **처음부터 슬라이스 패턴을 적용하지 않은 것**: 단일 스토어에서 시작해서 Phase 7~8에 분리했는데, 처음부터 했더라면 중간 리팩토링 비용이 없었을 것이다
- **테스트 커버리지 부족**: `geoUtils.ts`, `subwayMessageParser.ts` 등 핵심 유틸 함수의 단위 테스트를 더 일찍, 더 많이 작성했어야 했다. 후반부에 회귀 버그로 시간을 낭비하는 일이 있었다
- **API 정책 검토를 늦게 한 것**: ODsay 정책 제한(영구 캐싱 금지 등)을 초반에 깊이 검토했다면 캐싱 전략의 방향을 처음부터 다르게 잡았을 것이다
- **지역 버스 API 파편화 과소평가**: 처음에는 TAGO 하나로 전국 버스를 커버할 수 있다고 생각했다. 실제로는 경기도, 인천, 부산, 대전 각각 별도 API가 필요했고, 지역마다 스펙이 달랐다
- **완성되지 못한 Phase 2 기능들**: 택시 모드, 여정 캘린더, 후기 기능 등 사용자 경험을 풍부하게 할 기능들을 결국 구현하지 못한 것이 아쉽다

## 8. 다음에 비슷한 프로젝트를 한다면

1. **API 생태계를 먼저 조사하라**: 아이디어를 구상하기 전에 해당 도메인의 API 정책, 비용, 커버리지를 검토하라. 국내 대중교통 데이터는 개인 개발자에게 구조적 장벽이 높다

2. **처음부터 테스트를 작성하라**: 특히 파싱 로직, 계산 유틸, 지오스패셜 함수는 단위 테스트 없이 회귀 버그를 막을 수 없다

3. **슬라이스/모듈 패턴을 초기에 설계하라**: 상태 관리 구조는 나중에 바꾸기 매우 비싸다

4. **외부 API에는 항상 Fallback을 준비하라**: Circuit Breaker + Fallback 조합은 필수다. API가 언제 죽을지 모른다

5. **MVP를 먼저 완성하고 확장하라**: Phase 1~3의 핵심 기능이 완성된 시점에서 실제 사용자 피드백을 받았다면 방향이 달라졌을 수도 있다

## 9. 최종 소감

2달 동안 Next.js + Supabase + 네이버 지도 + 대중교통 API를 엮어 실제로 작동하는 웹앱을 만들었다. 처음에는 "경유지 경로 앱"이라는 단순한 아이디어였지만, 실시간 대중교통 정보, 지형 분류, ETA 정밀화, Circuit Breaker, Gaussian Decay 랭킹까지 예상보다 훨씬 넓은 기술적 여정이었다.

결국 "폐쇄적인 API 정책"과 "개인 개발자의 한계"라는 구조적 벽에 부딪혔다. 이는 실패가 아니라 현실을 배운 것이다. 아이디어의 한계가 아니라 생태계의 한계였고, 그것을 직접 부딪혀 알게 됐다.

코드는 남는다. 이 프로젝트에서 배운 아키텍처 패턴, API 통합 경험, 지오스패셜 연산, 모바일 UX 설계 등은 다음 프로젝트에서 분명히 쓰인다.
